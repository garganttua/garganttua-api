# Garganttua API Javalin Binding

## Description

`garganttua-api-binding-javalin` is a **pure dependency-bundle module** inside the `garganttua-api-bindings` group. It contains no Java sources of its own. Its sole purpose is to declare a single, version-pinned Maven dependency on **Javalin** (`io.javalin:javalin`) so that the rest of the framework — primarily the `garganttua-api-javalin` transport module — can pull in the library transitively without hard-coding its coordinates in multiple places.

The pinned version (`javalin.version` in the root POM) is currently **6.6.0**. Updating the entire framework to a new Javalin release requires changing exactly one property.

**Key Features:**
- **Single-version authority** — Javalin coordinates and version are defined once in the root POM `<properties>` block; every consumer inherits the same artifact without risk of split-brain versioning
- **Transitive delivery** — dependents of `garganttua-api-binding-javalin` automatically receive `io.javalin:javalin` and its own transitive closure (Jetty, Kotlin stdlib, Jackson, SLF4J) without extra declarations
- **Lightweight HTTP/WebSocket server** — Javalin 6.x is a Kotlin/Java-friendly layer over Jetty 12 that exposes a concise, lambda-based routing API, HTTP/2, WebSocket, and SSE out of the box
- **No framework lock-in** — keeping the binding in an isolated module means swapping or upgrading the HTTP layer in the future is a one-module concern

## Core Concepts

### What a binding module is

The `garganttua-api-bindings` group follows a pattern: **one external library, one submodule**. Binding modules never contain application logic. They act as the canonical version anchor for their wrapped library inside the `garganttua-api` build. This avoids Maven dependency-management sprawl and makes security audits simpler — there is exactly one place to review per third-party library.

### What Javalin provides

Javalin is a lightweight JVM web framework built on top of Jetty. It exposes HTTP routing via typed handler lambdas, supports virtual threads (Project Loom) natively from version 6, and integrates with Jackson for JSON serialization. The transport module that depends on this binding uses Javalin to host the REST endpoints generated by the `garganttua-api` engine.

### Version pinning

The property `javalin.version` is declared in the root `pom.xml` of `garganttua-api`:

```xml
<properties>
    <javalin.version>6.6.0</javalin.version>
</properties>
```

This binding's `pom.xml` references it as `${javalin.version}`, so the effective version is always inherited from that single source of truth.

## Usage

This module ships no Java sources. You never interact with it directly at the code level. Its intended consumers are:

1. **The `garganttua-api-javalin` transport module** — declares a compile-scoped dependency on this binding and receives Javalin transitively.
2. **Any other garganttua-api module** that needs Javalin — add this binding as a dependency instead of declaring `io.javalin:javalin` directly.

To pull Javalin into your own garganttua-api extension module, declare this binding as a dependency:

```xml
<dependency>
    <groupId>com.garganttua</groupId>
    <artifactId>garganttua-api-binding-javalin</artifactId>
    <version>3.0.0-ALPHA01</version>
</dependency>
```

Maven resolves `io.javalin:javalin:6.6.0` (and its transitive dependencies) automatically. You can then import and use Javalin classes directly:

```java
import io.javalin.Javalin;

Javalin app = Javalin.create(config -> {
    config.useVirtualThreads = true;
}).get("/health", ctx -> ctx.result("ok"))
  .start(8080);
```

To upgrade Javalin across the entire framework, change `javalin.version` in the root POM and rebuild. No other file needs to change.

## Tips and best practices

- **Never redeclare `io.javalin:javalin` directly** in another garganttua-api module. Always go through this binding — it is the single-version authority.
- **Check Javalin's transitive closure** before upgrading: Javalin 6.x depends on Jetty 12, Kotlin stdlib, and a specific Jackson range. Run `mvn dependency:tree -pl garganttua-api-binding-javalin` to inspect the full tree before bumping `javalin.version`.
- **Scope management** — if a module only needs Javalin at test time, declare the binding with `<scope>test</scope>`. The binding itself does not enforce a scope.
- **Virtual threads** — Javalin 6 supports Loom virtual threads via `config.useVirtualThreads = true`. This pairs naturally with garganttua-api's Java 21 baseline and improves throughput under high concurrency at near-zero thread-pool tuning cost.
- **Logging** — Javalin uses SLF4J. Make sure your application module includes an SLF4J binding (Logback, Log4j 2, etc.); otherwise Javalin emits a `SLF4J: No SLF4J providers were found` warning at startup.
